# First verdict — 2026-10-10

Every number below is `cpu_s median / C at the same level`, measured by
`drivers/arena.py`: one process per run, identical corpus (manifest sha256
verified across architectures), identical C frames handed to every decoder,
contestant order rotated per round, one core pinned, bytes oracle enforced on
every decode. 3150 timed runs and 140 oracle checks per architecture, 0 failures.

* runs: [38062303181](https://github.com/Gong-Mi/zstd-arena/actions/runs/38062303181) (head 60f2c88) and
  [38061716700](https://github.com/Gong-Mi/zstd-arena/actions/runs/38061716700) (head 2b684f9), used as a drift check.
  Commit 60f2c88 predates a history rewrite that only dropped an accidentally
  committed local work directory; its tree is identical to this document's commit
  outside `work-q/` and `tables.pkl`.
* x86_64 runner: AMD EPYC 9V74, 4 vCPU, pinned cpu2. aarch64 runner: 4 vCPU, pinned cpu2.
* contestants: `zstd-c` = facebook/zstd **v1.5.7** (one-shot `ZSTD_compress` /
  `ZSTD_decompressDCtx`); `ruzstd-release` = crates.io 0.9.0;
  `ruzstd-upstream` = KillingSpark/zstd-rs @ fe37617;
  `ruzstd-fork` = Gong-Mi/zstd-rs @ b4ea9a3; `zstd-rs-avarok` = crates.io zstd-rs 0.1.0.

## What both runs agree on

* **C is still the reference.** No Rust contestant matches libzstd 1.5.7 on both
  ratio and speed at the same level.
* **`zstd-rs` 0.1.0 (Avarok) is the closest Rust contestant**: 100.2–101.4% of C's
  size at L1/L3, 1.1–2.3x C's encode time, 1.07–1.56x C's decode time. Its README
  claims (ratio within ~1%, "native speed below C") reproduce here. Two findings of
  our own: on the all-zeros corpus it emits 209.8% of C's size (libzstd uses RLE
  blocks), and it is the only Rust contestant that matches C when decoding
  incompressible frames (0.99x).
* **Upstream ruzstd is far from C on ratio**: 111.6–140.9% of C's size at L1, and the
  L3 arm is not a level-3 comparison at all — `CompressionLevel::Default/Better/Best`
  are `UNIMPLEMENTED` upstream, so its L3 row is Fastest. At L1 it costs 1.2–17.8x
  C's encode time and 1.1–3.8x C's decode time.
* **The fork leads the ruzstd line on ratio and on decode, and pays time for it**:
  L1 size 104.5–105.2% of C on text/json/src vs upstream's 124.9–140.9%, 99.1–100.9%
  on ELF; decode typically 1.5–3.8x C (upstream 1.0–3.8x); on incompressible data it
  is 4.2–4.5x C against upstream's 17.5x.
* **`ruzstd-release` 0.9.0 and `ruzstd-upstream` fe37617 are indistinguishable here** —
  the unreleased commits after the 0.9.0 tag do not move these numbers.

## Who is chasing whom

1. Everyone is chasing C. Avarok is closest on both axes, then the fork, then upstream.
2. On the ruzstd line, upstream is chasing the fork: the fork's encoder work buys
   20–36 points of ratio (relative to C) upstream does not have, at 1.0–1.5x
   upstream's encode time.
3. Against the newcomer, the fork is the one chasing: Avarok is ahead on ratio and
   2–2.4x faster encoding, 1.3–1.9x faster decoding on the same corpora.
4. The fork's remaining edge: runs/RLE and incompressible data (88.2% vs 209.8% of
   C's size on zeros).

## Caveats

* Corpora are generated: 4 MiB text / src / elf, 1 MiB JSON, 1 MiB zeros, 4 MiB
  incompressible, plus a 4 KiB message case. The runner may substitute a
  synthesized fallback where a derived corpus is unavailable; the manifest records
  which path was used.
* The L3 arm only compares libraries that implement a level 3 (`zstd-c`, `zstd-rs`).
* Each contestant is measured through its own public API shape (C one-shot,
  ruzstd streaming decoder, `zstd-rs` one-shot with an output cap): process-level
  comparison, not a microbenchmark of one internal function.

Raw samples: artifacts of the runs above (`results-x86_64.json`, `results-aarch64.json`).
